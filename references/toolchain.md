# Инструменты и выбор архитектуры

Читай перед выбором стека или ответом «чем сделан сайт». Ниже зафиксированы инструменты прототипа мемной голосовалки и их назначение. Вечеринка, статичная шутка и сложный опрос могут требовать другой набор. Указанные имена исходников иллюстрируют структуру нового сайта; готовый код и доступы в этот пакет не входят.

## Чем сделан прототип

| Задача | Инструменты | Назначение и условия |
| --- | --- | --- |
| Смысл и тексты | Codex; `copywriting`, NMT-навыки `nmt-craft-value-proposition`, `nmt-craft-go-to-market` | От жизненного контекста к понятному обещанию и действию. Навыки помогают формулировкам; при их отсутствии работу можно выполнить самостоятельно. |
| Исходный интерфейс | HTML, CSS, JavaScript | Каноническая мобильная страница, мемы, формы и разрешённые счётчики. Для статичного прикола этого достаточно. |
| Frontend-хостинг | Framer; CLI `@framer/agent` или подходящий Framer MCP | В прототипе проверяли проект через `framer.getProjectInfo()`, затем code component, typecheck, preview и publish. Используй действующий доступный workflow; проект и сессию обнаруживай заново. |
| Интеграция во Framer | Node.js, React/TypeScript, code component с `iframe srcDoc` | Генератор брал канонический HTML и подставлял новый API origin. При таком подходе редактируй исходник и пересобирай производный компонент. Native Framer-компоненты допустимы, когда подходят лучше. |
| Сервер API и файлов | MCP Sites, Worker ES module, Fetch API | В прототипе backend отдельно обслуживал голоса, результаты, CSV и файлы. Перенос frontend во Framer не отменял backend. Можно выбрать другой доступный серверный хостинг. |
| Общая база | Cloudflare D1 через binding `env.DB`, SQL-миграция | Уникальный ключ и `INSERT ... ON CONFLICT DO NOTHING` защищали от повторной вставки. Для других правил, редактирования ответов и лимита мест нужна соответствующая атомарная операция. Подходит и другая транзакционная база. |
| Анонимный браузерный код | Web Crypto: `crypto.randomUUID()`, SHA-256, header `X-Vote-Token` | В cross-origin варианте код хранится в localStorage и отправляется API; реальные итоги — в базе. Same-origin вариант может использовать HttpOnly cookie. Это ограничение браузера, а не верификация человека. |
| Сборка | Node.js, shell, project build/validation scripts | Команды выбираются из созданного проекта. Не запускай отсутствующие скрипты только потому, что они встречаются в примере структуры. |
| Тесты API | `node:assert/strict`, `node:sqlite`, временная SQL-база | Повторные/параллельные запросы, ошибки, идемпотентность, сохранение, ограничения доступа и вместимость. Для другого runtime используй его подходящие тестовые инструменты. |
| Тесты клиентской логики | `node:vm`, assert, управляемые ответы API | Загрузка, ошибки, таймауты, повтор запроса и синхронизация интерфейса. Эти проверки дополняют живой браузер. |
| Мобильная и визуальная проверка | Внутренний браузер Codex, MCP `cua_repl`, доступные browser/Playwright API | DOM/снимки, форма, якоря, viewport 320/390/430 и другие размеры. В другом окружении используй доступный браузерный инструмент. |
| QR и печатный PDF | Python: `qrcode`, Pillow, ReportLab | QR кодирует окончательный публичный URL. PDF воспроизводит актуальные текст, дату и контакты. Нужны только если печатные материалы входят в задачу. |
| Проверка QR/PDF | Poppler или другой рендер PDF; `zxing-cpp`/`zxingcpp`, Pillow | Декодировать отдельный PNG и изображение отрендеренной PDF-страницы, сравнить оба адреса с окончательным сайтом. |
| Умеренные эффекты | 21st.dev как источник идей/компонентов; `framer-style-gate`, `animate` | Shine/shimmer, касание, короткое конфетти после подтверждённого нового действия. Доступные навыки помогают согласованности; эффекты адаптируются к стилю и reduced motion. |
| Проверки и ревью | `systematic-debugging`, `requesting-code-review`, `code-review-and-quality`, `receiving-code-review`, `verification-before-completion` | Это рабочие навыки агента, а не зависимости сайта. Применяй доступные по необходимости и проверяй наблюдаемый результат. |
| Работа с платформами и PDF | `framer`, `framer-code-components`, `sites`, `pdf` | Использовались в соответствующих частях прототипа. Следуй правилам доступных инструментов; не устанавливай чужой набор навыков ради самой ссылки на него. |
| Выдача | Codex `open_in_codex` и внутренний браузер, прямые ссылки; Printbox по запросу | Открыть результат сбоку, когда поддерживается. Открытие сервиса печати ещё не означает загрузку, печать или оплату. |

## Выбор под сценарий

- Статичная шутка или приглашение с готовой внешней ссылкой: статический frontend; база и собственный API не обязательны.
- Голоса, общий счётчик или RSVP: общий backend/подходящий сервис с реальным серверным хранением и правилами, проверяемыми на сервере.
- RSVP с вместимостью: транзакционная запись вместе с проверкой доступных мест и учётом изменения/отмены. Один уникальный код браузера не защищает вместимость от разных участников.
- Закрытые результаты: серверный доступ по роли/сроку и безопасное кэширование. Frontend-хостинг и CORS сами по себе не обеспечивают авторизацию.
- Framer + отдельный API: стабильный код браузера, точный allowlisted origin, preflight, читаемые ошибки и отсутствие зависимости от third-party cookies.

Если MCP, Framer, Sites или вспомогательный skill недоступен, выбери доступную подходящую альтернативу. Обязательный внешний доступ, который невозможно заменить, назови конкретно; не заявляй, что сайт опубликован или действие записано без подтверждения.

## Пример структуры будущего сайта

```text
web/index.html                 # канонический интерфейс
worker/index.js                # API при необходимости
migrations/                    # схема и миграции общей базы
scripts/build-framer.mjs        # генератор, только если выбран Framer
framer/MemeSite.tsx             # производный компонент
scripts/test-api.mjs            # проверки серверных правил
scripts/test-client.mjs         # проверки клиентского состояния
scripts/make-poster.py          # генерация QR/PDF по запросу
assets/                        # разрешённые мемы и другие медиа
```

Это пример организации, а не обязательные имена файлов. Не требуй у пользователя старую папку проекта, прежнюю сессию, production ID или конкретные мемы для запуска нового сайта.

## Последовательность для Framer + backend

1. Проверь подключение и текущий проект через MCP или доступный инструмент. При CLI-пути используй доступные Framer инструкции и project task map.
2. Определи назначение frontend и backend. Подставь настройки нового проекта: `FRONTEND_ORIGIN`, `API_ORIGIN`, идентификатор проекта, ключ browser-storage. Секреты держи вне публичных файлов.
3. Сделай механику в канонических исходниках, проверь её на изолированных данных. При отсутствии backend для реального общего действия не имитируй его локальным счётчиком.
4. Собери frontend/компонент. Для cross-origin API проверь CORS, OPTIONS и необходимые headers. Проверь повтор запроса со стабильным кодом, а отдельно — серверную авторизацию и сроки.
5. Выполни проверки, preview и публикацию в выбранное назначение. Проверь реальный адрес, форму и backend на телефоне, не добавляя тестовых production-записей.
6. После окончательного адреса создай QR/PDF, если они нужны, декодируй оба QR и используй версионные ссылки при замене файлов.
